## 1. 시스템 구성

### 1.1 수용 범위

㈜헤디 회신(2026-10)에 따라 아래 세 가지 구성을 **모두 수용**한다. 구성별로 서버를
따로 두지 않으며, 한 현장에 세 구성이 섞여 있어도 동작한다.

| 구분 | 데이터 경로 | 브로커 접속 주체 |
|---|---|---|
| 1안 | 측정모듈 → MQTT → 서버 | 측정모듈 |
| 2안 | 측정모듈 → RS-485 → 사용자 PC → MQTT → 서버 | 사용자 PC |
| 3안 | 측정모듈 → RS-485 → 브릿지 → MQTT → 서버 | 브릿지 |

### 1.2 구성 요소 정의

| 용어 | 정의 |
|---|---|
| 측정모듈(설비) | 변압기에 설치되어 수소가스·메탄가스·절연유 온도·유면을 계측하는 장치. 감시 대상의 최소 단위 |
| 브릿지 | RS-485 로 측정모듈을 폴링하여 모은 값을 MQTT 로 전송하는 보드 |
| 게이트웨이 PC | 2안에서 브릿지 역할을 대신하는 사용자 PC |
| 서버 | 수집 서버(MQTT 구독) · 데이터베이스 · 웹 화면으로 구성된 ㈜에스와이유 납품분 |

### 1.3 서버 측 데이터 구조상의 처리

세 구성의 차이는 **브로커에 접속하는 주체가 무엇인가**에 있을 뿐이며,
감시 대상은 언제나 측정모듈이다. 따라서 서버는 다음과 같이 저장한다.

| 구성 | 설비 등록 | 앞단(브릿지·PC) 등록 | 연결 방식 표기 |
|---|---|---|---|
| 1안 | 측정모듈 1대 | 없음 | 모듈 직결 |
| 2안 | 측정모듈 n대 | 사용자 PC 1대 | PC 경유 |
| 3안 | 측정모듈 n대 | 브릿지 1대 | 브릿지 경유 |

연결 방식은 장비가 사용한 토픽을 보고 서버가 자동으로 기록하므로,
별도 등록 절차가 필요하지 않다.

## 2. 통신 기본 사항

| 항목 | 규격 |
|---|---|
| 프로토콜 | MQTT 3.1.1 이상 (MQTT 5 가능) |
| 브로커 | Mosquitto 2.0.x, 서버에 설치 |
| 포트 | 8883 (TLS 필수). 1883 은 서버 내부(127.0.0.1) 전용 |
| 암호화 | TLS 1.2 이상. 서버 발급 CA 인증서를 장비에 탑재 |
| 인증 | 계정/비밀번호 방식. 계정은 ㈜에스와이유가 발급 |
| 접근 권한 | 발행은 `tele` · `stat` · `cmd/ack`, 구독은 `cmd` 만 허용 |
| QoS | 1 권장 (중복 수신은 서버가 제거) |
| Clean Session | false 권장 (일시 단절 시 명령 유실 방지) |
| Keep Alive | 60초 |
| 문자 인코딩 | UTF-8 |
| 페이로드 형식 | JSON |
| 시각 표기 | ISO 8601, UTC (예: `2026-10-09T01:23:45Z`). Unix epoch(초·밀리초)도 수용 |

**주의** — 장비 시계가 틀어지면 추세 그래프와 재전송분의 시각이 모두 어긋난다.
NTP 동기 또는 `sync_time` 명령 수신이 사실상 필수이다.

## 3. 토픽 체계 (v2)

### 3.1 기본 형식

```
dh/v1/{site}/{srcType}/{srcId}/{kind}
```

| 구성 요소 | 설명 | 값 |
|---|---|---|
| `dh/v1` | 토픽 접두사. 서버 설정으로 변경 가능 | 고정 |
| `site` | 현장 코드 | `dh1` |
| `srcType` | **브로커에 접속한 주체의 종류** | `module` · `gateway` · `bridge` |
| `srcId` | 그 주체의 고유 식별자 | 장비 업체 부여 |
| `kind` | 메시지 종류 | `tele` · `stat` · `cmd` · `cmd/ack` |

### 3.2 구성별 토픽 예시

| 구성 | 계측값 토픽 |
|---|---|
| 1안 | `dh/v1/dh1/module/MOD-7/tele` |
| 2안 | `dh/v1/dh1/gateway/PC-1/tele` |
| 3안 | `dh/v1/dh1/bridge/BR-1/tele` |

### 3.3 토픽 목록

| 토픽 | 방향 | 용도 | 설정 |
|---|---|---|---|
| `.../tele` | 장비 → 서버 | 계측값 | QoS 1 |
| `.../stat` | 장비 → 서버 | 접속 상태·펌웨어·신호세기 | QoS 1, retain, LWT 등록 |
| `.../cmd` | 서버 → 장비 | 명령 | QoS 1 |
| `.../cmd/ack` | 장비 → 서버 | 명령 응답 | QoS 1 |

### 3.4 v1 대비 변경점

v1 은 `dh/v1/{site}/bridge/{bridgeId}/...` 로 브릿지만을 전제하였다.
v2 에서는 **토픽이 발신 주체를, 페이로드가 대상 설비를 나타내도록 분리**하여
측정모듈과 게이트웨이 PC 가 직접 접속하는 구성을 함께 수용한다.

## 4. 메시지 규격

### 4.1 계측값 (`tele`)

#### 4.1.1 표준형 — 여러 설비분을 한 번에 (2안·3안)

```json
{
  "ts": "2026-10-09T01:23:45Z",
  "seq": 10421,
  "replay": false,
  "items": [
    { "deviceId": "DH-A-01", "ts": "2026-10-09T01:23:40Z",
      "h2": 11.9, "ch4": 3.4, "temp": 48.8, "oil": 1, "q": 0 },
    { "deviceId": "DH-A-02", "ts": "2026-10-09T01:23:41Z",
      "h2": 9.7,  "ch4": 2.8, "temp": 47.1, "oil": 1, "q": 0 }
  ]
}
```

#### 4.1.2 단일형 — 모듈이 자기 값만 (1안)

`items` 배열 없이 최상위에 값을 담는 형태도 수용한다.
이때 `deviceId` 는 생략할 수 있으며, 서버는 토픽의 `srcId` 를 설비 식별자로 쓴다.

```json
{
  "ts": "2026-10-09T01:23:45Z",
  "replay": false,
  "h2": 11.9, "ch4": 3.4, "temp": 48.8, "oil": 1, "q": 0
}
```

#### 4.1.3 필드 정의

| 필드 | 위치 | 필수 | 형식 | 설명 |
|---|---|---|---|---|
| `ts` | 공통 | 권장 | 문자열/숫자 | 측정 시각. 항목별 `ts` 가 있으면 그것을 우선 적용. 없으면 서버 수신 시각으로 대체 |
| `seq` | 메시지 | 선택 | 정수 | 발신 순번. 누락 구간 추적용 |
| `replay` | 메시지 | 조건부 필수 | 불리언 | 버퍼에 쌓였다가 뒤늦게 보내는 과거분이면 `true`. 제6항 참조 |
| `items` | 메시지 | 선택 | 배열 | 설비별 계측값 목록. 생략 시 단일형으로 간주 |
| `deviceId` | 항목 | 1안 외 필수 | 문자열 | 설비 식별자. **브릿지·모듈을 교체해도 바뀌지 않아야 한다** |
| `h2` | 항목 | — | 실수 | 수소가스 (ppm) |
| `ch4` | 항목 | — | 실수 | 메탄가스 (ppm) |
| `temp` | 항목 | — | 실수 | 절연유 온도 (℃). `temperature` 도 수용 |
| `oil` | 항목 | — | 정수/문자열 | 절연유 유면. 제9.1항 협의 필요 |
| `q` | 항목 | 선택 | 정수 | 품질 코드. 통신단절과 센서 고장을 구분하기 위한 예비 필드 |

측정 항목(`h2`·`ch4`·`temp`·`oil`)은 값이 없으면 필드를 생략한다.
`null` 로 보내도 무방하며, 서버는 해당 항목의 등급을 직전 값으로 유지한다.

#### 4.1.4 서버 측 처리

| 상황 | 서버 동작 |
|---|---|
| 같은 `(deviceId, ts)` 중복 수신 | 중복 제거 후 1건만 저장 |
| 과거 시각 값이 뒤늦게 도착 | 이력에만 저장. 현재값을 밀어내지 않음 |
| 등록되지 않은 `deviceId` | 설비를 임시 등록하고 수신 내역에 경고. **값은 버리지 않음** |
| JSON 형식 오류 | 수신 내역에 원문과 오류 사유 기록 |
| `items` 가 빈 배열 | 수신 내역에 오류 기록 |

### 4.2 상태 (`stat`)

```json
{ "online": true, "ts": "2026-10-09T01:23:45Z",
  "fw": "1.2.3", "rssi": -62, "interval": 60 }
```

| 필드 | 필수 | 설명 |
|---|---|---|
| `online` | 필수 | 접속 상태 |
| `fw` | 권장 | 펌웨어 판번호 |
| `rssi` | 선택 | 무선 신호세기 (dBm) |
| `interval` | 선택 | 현재 설정된 측정 주기(초). 1안에서 특히 유용 |
| `deviceId` | 선택 | 1안에서 토픽의 `srcId` 와 설비 ID 가 다를 때만 |

- retain 을 설정하고, LWT(Last Will and Testament)로 `{"online":false}` 를
  등록할 것을 권장한다. 장비가 비정상 종료해도 화면에 즉시 반영된다.
- 브릿지·게이트웨이가 보내면 앞단의 상태로, 모듈이 직접 보내면 해당 설비의
  상태로 기록된다.

### 4.3 명령 (`cmd`)

서버 → 장비 방향이다. 장비는 자신의 `.../cmd` 토픽을 구독한다.

```json
{
  "cmdId": 1024,
  "command": "set_interval",
  "deviceId": "DH-A-01",
  "params": { "seconds": 60 },
  "ts": "2026-10-09T01:30:00Z"
}
```

| 필드 | 설명 |
|---|---|
| `cmdId` | 명령 식별자. **응답에 같은 값을 그대로 넣어야 한다** |
| `command` | 명령어 |
| `deviceId` | 특정 설비 하나를 지정하는 명령일 때만 포함 |
| `params` | 명령별 추가 값 |

#### 4.3.1 명령 목록 (협의 요청)

| 명령어 | 용도 | `params` |
|---|---|---|
| `ping` | 생존 확인 | 없음 |
| `read_now` | 즉시 측정 후 전송 | 없음 |
| `resend` | 지정 구간 재전송 | `from`, `to` (ISO 8601) |
| `set_interval` | 측정·전송 주기 변경 | `seconds` (10~3600) |
| `sync_time` | 장치 시계를 서버 기준으로 동기 | 없음 |
| `reboot` | 장치 재시작 | 없음 |

위 명령 집합은 서버 측 제안안이다. 지원 가능 범위와 명령어 표기를
확정해 주시기 바란다(제9.3항).

### 4.4 명령 응답 (`cmd/ack`)

```json
{
  "cmdId": 1024,
  "ok": true,
  "ts": "2026-10-09T01:30:00Z",
  "result": { "interval": 60 }
}
```

실패 시:

```json
{ "cmdId": 1024, "ok": false, "error": "지원하지 않는 명령입니다." }
```

| 필드 | 필수 | 설명 |
|---|---|---|
| `cmdId` | 필수 | 수신한 명령의 `cmdId` 를 그대로 반환 |
| `ok` | 필수 | 수행 성공 여부 |
| `error` | 실패 시 | 실패 사유 |
| `result` | 선택 | 명령별 결과값 |

## 5. 명령 응답 시간

㈜헤디 회신: **네트워크 상태에 따라 다르지만 1초 이내 응답**.

| 항목 | 값 |
|---|---|
| 장비 응답 목표 | 1초 이내 |
| 서버 대기시간 | 기본 10초 (운영 화면에서 1~120초 범위로 조정) |
| 초과 시 처리 | 해당 명령을 "응답 없음"으로 정리 |
| 늦게 도착한 응답 | 응답 없음으로 정리된 뒤에 도착해도 정상 반영 |

서버 대기시간을 장비 규격(1초)보다 넉넉히 둔 이유는, 브로커 경유 왕복 지연과
무선 구간의 일시적 지연을 응답 실패로 오판하지 않기 위함이다.
v1 에 기재한 10초는 유지하되, 운영 중 조정 가능하도록 변경하였다.

## 6. 미전송분 재전송 규칙

㈜헤디 회신: **브릿지 내부 미전송 데이터 최대 1개월분 저장 가능**.

### 6.1 재전송 표시

과거분을 뒤늦게 보낼 때는 반드시 `"replay": true` 를 넣어야 한다.
이 표시가 있으면 서버는 다음과 같이 처리한다.

| 처리 | 내용 |
|---|---|
| 이력 저장 | 수행 |
| 현재값 갱신 | **수행하지 않음** |
| 알람 발생 | **수행하지 않음** |

`replay` 표시가 없으면 서버는 그 값을 현재 상태로 간주한다. 1개월 전의
이상값으로 알람이 울리고 관계자에게 문자·카카오톡이 발송되는 사고가 되므로,
**이 필드는 생략해서는 안 된다.**

### 6.2 분할 전송 규칙

| 항목 | 값 | 비고 |
|---|---|---|
| 한 메시지 최대 항목 수 | **500개** | 서버 설정값. 초과분은 수용하지 않고 수신 내역에 경고 기록 |
| 메시지 간 간격 | 200ms 이상 권장 | 브로커·DB 과부하 방지 |
| 전송 순서 | 오래된 값 → 최근 값 | 권장 |

### 6.3 데이터량 산정

1분 주기 · 브릿지당 32대 · 30일 기준으로 한 브릿지의 1개월분은 약 **138만 건**이다.
500개 단위로 나누면 약 2,760개 메시지가 된다.

서버 측 검증 결과(3대 × 5분 간격 × 30일 = 25,920건, 500개 단위 52개 메시지)
전량이 약 10초 내에 적재되었고, 현재값·알람에는 영향이 없음을 확인하였다.

### 6.4 서버에서 재전송을 요청하는 경우

운영자가 특정 구간의 누락을 발견하면 `resend` 명령으로 재요청한다.
중복은 서버가 제거하므로, 요청 구간이 겹쳐도 무방하다.

## 7. RS-485 구성 제약 (2안·3안)

㈜헤디 회신: **브릿지당 최대 32대 지원. 단, 현장 환경에 따라 영향받을 수 있음**.

| 항목 | 값 |
|---|---|
| 브릿지·PC 1대당 측정모듈 최대 | 32대 |
| 서버 측 처리 | 등록 화면에서 앞단별 등록 대수를 `n / 32` 로 표시하고 초과 등록을 거부 |
| 한도 초과 상태로 값이 올라올 경우 | 값은 저장하고 수신 내역에 경고 기록 |

현장 환경에 따라 수용 대수를 낮춰야 하는 경우, 서버에서 앞단별로 한도를
개별 조정할 수 있다.

## 9. 협의 요청 사항

### 9.1 절연유 유면 측정 규격 (최우선)

현재 서버는 유면을 **2치(정상/낮음)** 로 저장하며, 접점(0/1)·문자열·숫자를
모두 수용한다. 다음 중 어느 방식인지 확정이 필요하다.

| 방식 | 서버 영향 |
|---|---|
| 접점 2치 (정상/낮음) | 변경 없음 |
| 아날로그 (% 또는 mm) | 데이터 형식·임계치 체계·화면 게이지 변경 필요 |

아날로그인 경우 측정 범위와 단위, 그리고 "낮음" 판정 기준값을 함께 알려주시기 바란다.

### 9.2 식별자 부여 규칙

| 항목 | 확인 필요 사항 |
|---|---|
| `deviceId` | 부여 주체와 형식. 설비 교체 시에도 유지되는 값인지 |
| `srcId` | 브릿지·모듈의 고유 ID 형식 (시리얼 번호 사용 가능 여부) |
| RS-485 슬레이브 주소 | `deviceId` 와의 대응 관계 |

### 9.3 명령 집합 확정

제4.3.1항의 명령 중 지원 가능한 범위와 명령어 표기를 확정해 주시기 바란다.
서버는 명령 정의를 한 곳에서 관리하므로, 확정 후 반영에 추가 공수가 들지 않는다.

### 9.4 접속 정보 전달

브로커 주소·포트·계정·CA 인증서를 ㈜에스와이유가 발급하여 전달한다.
계정은 장비 구분별로 분리 발급할 수 있으므로, 필요한 단위(현장 단위 /
브릿지 단위 / 모듈 단위)를 알려주시기 바란다.
